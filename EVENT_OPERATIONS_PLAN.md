# Event Operations Implementation Plan

Status: Step 1 (audit + foundation) complete. No application code has been changed — this and `SUPABASE_CONNECTION_PENDING.md` are the only new files. Everything below is the plan to execute in later, approved steps.

## Audit summary

Reviewed: full route tree (`app/*`), all components, `lib/`, every Supabase migration, `types/`, theme (`app/globals.css`), and how the app talks to Supabase.

- Stack: Next.js App Router + Supabase (`@supabase/ssr`), Tailwind v4 with a warm gold/cream theme in CSS variables, Inter Variable font, shadcn primitives in `components/ui/`. One consistent design language throughout — nothing to unify, just to extend.
- Auth today: a single business-owner login via `profiles` (1:1 with `auth.users`). No role concept, no staff login, no department concept exist yet.
- Data model is single-owner: every business table carries `owner_id` and RLS policies check `auth.uid() = owner_id`. This is the central fact that shapes the whole staff-access design (full detail in `SUPABASE_CONNECTION_PENDING.md`).
- `staff_members` exists today only as a name/phone directory for assigning bookings — no login, no department.
- Quotes are not a separate feature — they're `bookings` rows with `is_quote = true`. A "job" does not exist as its own concept yet; the booking itself is the unit of work.
- Existing adjacent features that the new workflow should extend, not duplicate: the notes-marker-based "modifications" queue, and the single-row `rental_returns` / `process_rental_return` mechanism for rental bookings.
- Business logic that changes data is implemented as Postgres RPC functions (`create_booking`, `change_booking_status`, `record_booking_payment`, `process_rental_return`), called via `.rpc()` from the client — an established, good pattern to keep following for the new workflow's actions.
- Baseline health check: `tsc --noEmit` passes with zero errors across the whole project right now. (`npm run lint` / `npm run build` could not be run from this automation session — see note at the end.)

## Target model (confirmed with user)

Two portals only — Admin and Staff. One confirmed booking = one central Event Job. Departments are staff-portal views, not separate portals: booking, warehouse, qc (quality check + packing + return QC), stylist, collection, modification. Travel/accommodation is an admin-only module. Only booking-department staff can close an event.

Flow: Lead/Quote → Booking → Booking Confirmed → Central Event Job → Warehouse → QC & Packing → Event → Collection → Return QC → Return Warehouse → Booking Final Check → Close Event → Event Closed, with Stylist Opportunity → Interest → Admin Approval → Travel/Accommodation running in parallel from the moment the booking is confirmed.

## Proposed build order (phased, so each piece can be checked before the next lands)

1. **Foundation**: `profiles.role`, `staff_members` login/department columns, Manage Access tab on the existing Staff page. Built against local/mock state per the Supabase-deferral rule; real auth wiring recorded in `SUPABASE_CONNECTION_PENDING.md` §1–2.
2. **Core pipeline**: Central Event Job + stages, Staff Portal shell (same theme, department-gated nav), Warehouse pick screen, QC/Packing screen. (§3–5)
3. **Stylist track**: Opportunity/interest list, admin Approval module, admin-only Franchise Travel module. (§6–7)
4. **Close-out**: Collection screen, Return QC/Return Warehouse (reactivating the same QC/Warehouse views), Booking Final Check + Close Event with its department-only authorization. (§8–9)

## Open items needing a decision before Phase 4

`process_rental_return` and the pickup/due-date fields only exist for `booking_type = 'rental'` today — there's no return concept at all for sale bookings. The described Collection → Return QC → Return Warehouse leg needs a decision: does it apply to rentals only, or to sale bookings too? Flagged in `SUPABASE_CONNECTION_PENDING.md`, not yet resolved.
